# PR 6194: static gnoweb previews for pull requests

Reviewing a realm change means reading `Render()` and imagining the markdown, or
checking the branch out and running `gnodev`. This publishes the rendered page
instead, on a URL in the pull request comment.

## What triggers a preview

| Diff touches | Rendered |
|---|---|
| `examples/gno.land/r/**` | that realm |
| `examples/gno.land/p/**` | every realm that transitively imports it |
| `gno.land/pkg/gnoweb/**`, `gno.land/cmd/gnoweb/**`, `contribs/gnodev/**` | a fixed sample, plus screenshots |

Anything else produces no artifact, no comment and no job. Excluded because they
cannot change what a realm renders: `*_test.gno`, `*_filetest.gno`, `filetests/`,
`examples/quarantined/**`, and `ignore = true` packages. Realms under
`gno.land/r/tests/` are previewed when changed directly but never pulled in as
dependents — they are VM fixtures, and a change to a widely imported package
would otherwise crowd out the realms the pull request is about.

## Design

`misc/gnopreview` boots `gnodev` on just the selected packages (dependencies
resolve lazily from `examples/`), crawls the resulting gnoweb over HTTP, and
writes a self-contained static tree. It never talks to a chain: realms show their
state immediately after `init()`.

**The trust split is the load-bearing part.** Most pull requests come from forks,
where the `pull_request` token is read-only, so the job that renders — which by
construction runs the pull request's own code, including its own copy of the
workflow — can never be the job that publishes.

| Workflow | Trigger | Token | Runs PR code |
|---|---|---|---|
| `pr-preview.yml` | `pull_request` | read-only, no secrets | yes |
| `pr-preview-publish.yml` | `workflow_run` | deploy key + comment write, through an environment | no |
| `pr-preview-cleanup.yml` | `pull_request_target: closed` | deploy key, through an environment | no |

Not running the pull request's code is not enough on its own, because what the
publishing job publishes *is* the pull request's work: HTML and, for a gnoweb
change, script, served from `gnolang.github.io`, the origin every gnolang Pages
site shares. A fork can also drop any gate from its own copy of
`pr-preview.yml`, or add a second workflow with the same `name:`. So publishing
is gated on who is asking, decided in a job that holds no secret:

- **Both the author and the run's triggering actor can write to the
  repository** → environment `gno-previews`, no reviewers. Both, because either
  can put code in the snapshot (a maintainer's "Update branch" on an outsider's
  pull request makes the maintainer the actor).
- **Anyone else, forks included** → environment `gno-previews-review`, with
  required reviewers. Approving the deployment is the review; approving a fork's
  CI run only lets the untrusted half render. If that environment has no
  required reviewers the job refuses to publish, because GitHub creates a
  missing environment unprotected on first use.
- The deploy key exists **only** as a secret of those two environments.
- The run must come from `.github/workflows/pr-preview.yml`, checked on
  `workflow_run.path`, so a same-named look-alike is ignored.

Four consequences of that split are easy to get wrong, and were:

- **The pull request number must come from the `workflow_run` payload**, never
  from the artifact. A fork controls the render job entirely, so a number written
  there would let it replace another pull request's preview and edit that pull
  request's bot comment.
- **The artifact is untrusted data.** A `.git` directory inside it turns
  `pr-<N>/` into a gitlink, which GitHub Pages reports as a build error — failing
  publication for every preview, not just the one. It is stripped, and the
  snapshot is size-capped.
- **The privileged job executes nothing from outside this repository.** The
  landing page on the previews repo is regenerated by that repository's own
  workflow with its own token.
- **The comment is not the render job's.** It would be posted as
  `github-actions[bot]`, so the publishing job builds it with the default
  branch's `gnopreview comment` from the artifact's `preview.json`: package
  paths must be plain paths, and every link, image path and caption is derived
  again from the realm name and that binary's own tables.

The sticky comment is matched on the bot's authorship as well as its marker, so a
comment someone else posts containing the marker is not adopted and edited.

## Where previews are published

A separate repository, `gnolang/gno-previews`, on its own Pages site in branch
mode — not this repository's Pages site, and `deploy-pages.yml` is unchanged.

The two workloads want opposite things. The godoc mirror is regenerated from
scratch on every deploy (measured: 2 m 57 s) and nobody needs it within five
minutes of a merge. A preview's whole value is being there when a reviewer clicks
the link. A Pages site built by an Actions workflow has **no incremental
deploy** — the entire site ships every time — so sharing one would rebuild and
re-upload the documentation for every preview push. Branch-published, a preview
is one incremental push: measured **33 seconds** from push to serving, against
3–6 minutes through the shared artifact.

Separation also bounds the blast radius (a broken preview job cannot delay the
documentation), and gives previews their own 1 GB budget and a history that can
be squashed freely.

Write access is a deploy key rather than a fine-grained token: it cannot reach
another repository, does not expire, and carries no personal identity.

Configuration, on `gnolang/gno`:

- `GNOWEB_PREVIEW_BASE_URL`, a repository variable: where the previews site is
  served from, `https://gnolang.github.io/gno-previews`. Unset means publishing
  and cleanup do not run. Rendering always runs on `gnolang/gno`, because a
  `pull_request` run from a fork does not see repository variables; elsewhere
  the variable is also what turns rendering on.
- `PREVIEWS_DEPLOY_KEY`, the private half of a write-enabled deploy key on
  `gnolang/gno-previews`, as a secret of the environments `gno-previews` and
  `gno-previews-review` and nowhere else.

## Bounds

The 1 GB site cap binds long before anything else. With 36% of pull requests
touching preview-relevant paths, an open set of ~218 implies roughly 78 live
previews. So:

- Per-file `$source` pages are rendered **only for files the pull request
  touched**. They were 133 of 243 pages and 13.3 MB of 22.2 MB on a change to
  `p/nt/avl/v0` at the 25-realm cap; restricting them brought that to 8.8 MB /
  110 pages. A realm pulled in by a dependency gets none; when gnoweb itself
  changed, each keeps two, because there the rendering of a source file is what
  needs reviewing.
- The crawl skips URL shapes that enumerate rather than describe: `$state&oid=`
  and `&tid=` walk the realm object graph and trip gnoweb's own rate limiter,
  bare `$state` is ~1.3 MB per realm of a chain that only ran `init()`,
  `$help&func=X` repeats what `$help` already lists, and `$download` is bytes
  rather than a page.
- Caps, each measured against the worst case above: 25 realms (changed realms
  are rendered first), 400 pages per render, 10 render-argument pages per realm,
  and at publish time 20 MiB and 1,000 files per preview (apparent size, so
  empty files are not free). Past the realm cap a changed realm is still named
  in the comment, without a link to a page the snapshot does not hold.
- `gno-previews` evicts daily: closed pull requests, then previews quiet for 21
  days, then a 700 MiB budget least-recently-updated first. Between two sweeps,
  publishing refuses to take the whole site past 900 MiB.
- Every job has a timeout, and each browser run a 60 s deadline, so a hung
  gnodev or Chrome costs minutes, not the six-hour default.

## Details worth knowing

- **Output paths never contain `$`, `:` or `&`.** gnoweb puts the tab and the
  render arguments in the path (`$source&file=x`, `:p/about`); those are slugged
  under `_t/` and `_a/`. A slug that is not already a safe path segment carries a
  digest of its input, because otherwise `:p/a-b`, `:p/a/b` and `:p/a&b` collapse
  onto one file — and `:..` would fold onto the realm's own render page.
- **The trailing slash is semantic.** `/r/x/y` renders and `/r/x/y/` lists; they
  are different pages (62,174 vs 48,642 bytes for `r/gnoland/home`). The listing
  is left to the live site rather than aliased onto the render.
- **`public/js/index.js` builds its dynamic `import()` specifiers from a
  hardcoded `/public/js/controller-` prefix.** Served from any path but the site
  root, every controller 404s and the snapshot silently loses its interactive
  behaviour. The renderer relativises absolute `/public/` references inside
  copied assets, and warns if that string ever disappears. A one-line gnoweb fix
  using `import.meta.url` would remove the need.
- **Screenshots are taken over HTTP, not `file://`.** Chrome refuses to load ES
  modules from `file://`, so a `file://` screenshot is silently the no-JS
  rendering — measured: 0 controllers initialise versus 3 over HTTP. The renderer
  serves the snapshot on a loopback port for the duration.
- **Every page is `noindex, nofollow`.** A snapshot is a near-duplicate of a real
  gno.land page and must not compete with it in search results. gnoweb's layout
  emits `<meta name="robots" content="index, follow">`, which is *replaced*
  rather than supplemented: two conflicting directives leave the outcome to each
  crawler. A `robots.txt` `Disallow` would be worse — it prevents the crawler
  from ever reading the `noindex`.
- **Changed realms are shown before and after**, rendered from a checkout of
  the base the pull request merges into (the first parent of GitHub's merge
  commit, not the merge base, which would count everything that landed on
  master since as this pull request's change) with the head's gnodev and the
  head's assets, so the pair differs by the realm change alone. A realm that
  does not exist on the base is reported as new; a base pass that ran and failed
  is not.
- **Readiness is gnoweb's own `/ready`, body included.** Probing a realm page
  instead waited out the whole timeout when that realm failed to load, and a
  bare 200 is what any server already on the port answers: observed, a stray
  local server's catch-all page crawled as the preview. The ports are also
  checked free before gnodev starts.

## Known limits

Transactions, the faucet and search do not work — there is no signer and no
chain. Realms render post-`init` state, so one that is only interesting once it
holds data looks empty. Links out of the previewed set go to the live site, which
may show a different version of the realm than the branch.
