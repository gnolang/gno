# ADR: Sanitize `<gno-…>` tags at block start, isolate nested fences, and allow container `<gno-icon />`

## Status

Proposed (coordinated chain upgrade required).

## Context

`p/nt/markdown/sanitize` (implemented on top of `chain/markdown` natives) neutralizes dangerous constructs in user-supplied markdown before rendering in `gnoweb`. Several vulnerabilities and inconsistencies emerged around block tags, fenced code blocks, and extension tags:

1. **Issue #6300 (Fence inside list items):** A code fence indented under a list item (e.g. `- a\n  ```\n<gno-form path="x">\n```\n`) caused the sanitizer's line loop to enter fence mode (`inFence = true`). However, CommonMark §5.2 dictates that an unindented non-blank line (`<gno-form ...>`) cannot be part of the preceding list item, terminating both the list item and its nested code block. Goldmark parsed `<gno-form>` as a document-level element, rendering a live interactive form, while the sanitizer skipped escaping. Furthermore, the trailing fence line was treated by Goldmark as opening an unclosed code block at document level, swallowing subsequent page chrome and realm footers.
2. **Indented Fences (0–3 spaces):** An initial fix attempt (commit `d9a07e79a`) restricted fence tracking to column 0 (`if i != 0`), ignoring fences indented 1–3 spaces. Under CommonMark §4.5, top-level fences may be indented 0–3 spaces. Ignoring them caused bypasses where indented fences followed by fences/tags (such as ` ~~~\n~~~\n<gno-columns>` and ` ```\nx\n```\n<gno-columns>`) caused subsequent closing fences to be misinterpreted as openers, leaving `<gno-columns>` live. Unclosed indented fences also failed to auto-close at EOF, swallowing realm footers.
3. **Container `<gno-icon />` Rendering:** `<gno-icon />` is an inline extension meant to render in user content. The old line-start escape never reached an icon after a list or quote marker. Extending the escape to block start after those markers would have escaped `- <gno-icon ...>` and `> <gno-icon ...>`, so icons need an exemption there.
4. **Indentation and PR #6298 Harmony:** PR #6298 introduced backslash placement before 4+ spaces of indent for `<gno-button>`. For general extension delimiters, placing the backslash after indentation (`    \<gno-card>`) preserves indented code blocks per CommonMark while leaving `indentColumns` unused.
5. **The fence tracker cannot follow goldmark everywhere.** Goldmark measures a fence's indent from the column of the container it sits in; the sanitizer measures it from the start of the line and does not model list items, HTML blocks, or tab stops after `> `. Each mismatch lets a line the sanitizer counts as code be read by goldmark at block start, or the reverse: `- ```\n  ```\n  <gno-form …>` (a fence opened on the list marker line), a closer 3 columns into a list item, `<div>\n```\n\n<gno-form …>` (an HTML block hiding the fence line), and a tab after a blockquote prefix all rendered a live form.

## Decision

1. **Unified Fence Detection:**
   - The Rich pre-pass, the bracket walker and the line loop all detect fence openers with `parseFenceOpener`: 0–3 leading spaces, and the CommonMark §4.5 info-string rule (no backtick in a backtick fence's info string).
   - The bracket walker runs the fence check once per line, at the line's first byte, and lets `parseFenceOpener` take the indent. Re-running it at every leading space made the walker quadratic in the indent (1 MiB of spaces took 12 s, against 5 ms before) and accepted a fence at any indent, so `    ```\n[home]: https://evil.example` kept a link reference definition that goldmark reads at document level. A backslash before a newline is a hard break, so the walker still reads the next line as a line start.
   - Fences remain open until a valid closing fence (`isCloseFence`) or EOF. The EOF auto-close is written at the opener's column: at column 0 it would end a list item holding the fence and open a new fence over the realm's chrome.
2. **Fence Termination by Indent (Rich mode):**
   - A fence inside a list item ends, in goldmark, at the first non-blank line indented less than the item's content, and that line then parses at document level. Rich mode keeps list markers, so it must not leave such a line inside its fence state.
   - Rather than track list items, a pre-pass (`closeFencesAtDedent`) writes a closer at the opener's column before the first non-blank line indented less than the opener, and moves a closer that sits left of its opener to the opener's column. A closer at the opener's column ends the fence whether or not the fence sits in a list item, so goldmark and the sanitizer agree on every line after it.
   - The pre-pass runs before the bracket walker and the line loop, so neither applies an indent rule of its own. Applying it in each pass separately let them disagree: the walker deletes link reference definitions, so a definition that ended a fence by its indent was gone by the time the line loop ran, and the loop took the user's next fence line as a closer where the walker had taken it as an opener. `- a\n  ```\n[x]: u\n```\n[home]: https://evil.example` then kept the second definition live.
   - In strict mode (`EscapeBlockHazards`), list markers are escaped into text paragraphs, so all fences operate at document level and close only upon explicit fence closers or EOF. That includes empty list items: `listMarkerEnd` accepts a marker at the end of the line, so `-`, `*`, `+`, `1.` and `1)` alone are escaped too, wherever one starts a list: at the start, after a blank line, a fence or indented code. Inside a paragraph an empty item cannot interrupt it and is left alone, since escaping the `1)` that ends a link destination on the line before would change the link on a second pass.
3. **The walker's spans never hide a fence line.** A link, image or definition never spans a fence-shaped line: the fence ends goldmark's paragraph first. A span that did would hide the fence from the walker while the line loop and goldmark open it, and a deleted definition would take the fence line with it: after the pre-pass had paired that line with a closer, the closer became an opener, and `- x\n[foo]:\n  ```\n<gno-form …>` rendered a live form. The walker also refuses a definition whose destination line opens any block (`[foo]:\n  ```` ends the paragraph first) or that has text after its destination or title (CM §4.7: `[a]: u ```` is no definition, and deleting it up to the fence run left that run at column 0, where the fence trackers never saw it). It deletes a definition together with its 0–3 space indent, which would otherwise indent the line after it. In Rich mode, when a deleted definition puts a new line first, that line gets the setext escape `sanitize.BlockRich` gave the old first line, so a second pass changes nothing. A forward-only finder (`fenceLineFinder`) answers "is there a fence line in this span" with each line parsed once, since rejected candidates can nest over the same lines.
4. **A fence-tracking mismatch must not be exploitable.** Since the tracker cannot match goldmark in every container (Context 5), the hazards are neutralized on lines it counts as code too, as `<gno-button />` already was:
   - a `<gno-…>` tag at block start on a fenced line is escaped;
   - a fenced line shaped like a link reference definition (content starting with `[`, closed by `]:` before any other `[` or a blank line) or an alert marker (`[!` after a blockquote marker `>`) has its `[` escaped by the walker, so it cannot define a link or render a live alert for the page;
   - a line-start HTML tag (`<`, or `</` and any spaces, then a letter: a superset of CM §4.6 type 6 and 7 openers) is escaped when a fence line follows it before the next blank line, so no HTML block hides that fence from goldmark. Tags with no fence line after them are left alone: gnoweb drops their HTML, and escaping would show it.
   - The type 1 opener check accepts a form feed after the tag name, as goldmark's `\s` does: `<script\f` otherwise opened a block running to the end of the page.
   - Unlike the first two, the HTML escape removes a mismatch rather than tolerating one, and it is the only one at document level. The others only need to cover hazards that act on the whole page (extension tags, link definitions, alerts): every other mismatch sits inside a list item or quote, which ends before the realm's chrome.
5. **Shared Container Prefix Handling & `<gno-icon />` Policy:**
   - Implement `parseContainerPrefix` to scan leading indentation and CommonMark container markers (`>`, `- `, `* `, `+ `, ordered digits). It and `escapeLineLeader` parse list markers through one helper, `listMarkerEnd`.
   - In `escapeGnoExtDelimiters`, escape any unescaped `<gno-…>` or `</gno-…>` at block start.
   - Allow `<gno-icon ...>` openers to remain unescaped when preceded by container markers (`hasContainer == true`) or mid-line. Keep `<gno-icon ...>` at line start (no container) escaped to maintain parity with existing golden tests.
6. **Consistent Backslash Placement:**
   - Always insert the escaping `\` after leading indentation and container markers directly before `<`, e.g. `    \<gno-card>`, rendering safely as an indented code block containing literal text.
7. **Gas:** the `EscapeBlockHazards` and `EscapeBlockHazardsRich` slopes in `gnovm/stdlibs/native_gas.go` are scaled by the ratio of this change's slowest shape to the old native's calibration shape `[a]: u
(x
`, both timed alternately in one process at 100 KB: ×2.45 for strict (slowest: 16× `[a]: u\n(x\n` then `\n to the end, exercising repeated title-scan interruption checks) and ×2.95 for Rich (slowest: ~75% `  ```\nx\n` + 64× `[a]: u\n(x\n` + `\n to the end, where post-expansion growth combines with title interruption walks). The slopes were scaled, not re-fit on the reference machine. To keep per-line work down, the Rich pre-pass jumps between fence runs instead of visiting every line, and copies the input only when it changes something.

## Alternatives Considered

- **Tracking only column-0 fences (`d9a07e79a`):** Rejected because CommonMark permits top-level code fences indented 1–3 spaces. Ignoring them opened critical bypasses for `<gno-columns>` and caused page chrome swallowing.
- **Tracking list items (`curListIndent` / `fenceInList`):** An earlier revision of this PR ended a fence on a dedent only when it had seen the fence open inside a list item. A blank line (`- a\n\n  ```\n<gno-form path="x">`) and a lazy continuation line (`- a\nb\n  ```\n<gno-columns>`) both reset its list state while goldmark kept the item open, so the tag rendered live and the realm footer was lost. Empty list items (`-` alone on a line) would be a third gap. In the other direction, lines shaped like list markers that goldmark does not open a list for (a thematic break `* * *`, or `2. item` right after a paragraph) made it leave a document-level fence without a closer, so the fence ran over the realm's chrome. Modelling goldmark's list rules line by line is what #6300 calls fragile; the indent rule needs none of it.
- **Exiting fence state on a dedent without writing a closer:** Correct only when the fence really sits in a list item. For a document-level fence indented 1–3 spaces, goldmark keeps the dedented line as code and treats the user's next fence line as the closer, so the sanitizer's EOF auto-close would open a new fence over the realm's chrome. The written closer makes both readings agree.
- **Measuring fence indents from the container's column:** Would close the mismatches in Context 5 at their source, but needs the same container model (list items, blockquotes, tab stops, HTML blocks) that the list-tracking alternative failed to get right. Decision 4 makes a mismatch harmless instead. A fence inside a list item or a quote cannot reach the realm's chrome either: the chrome starts at column 0 after a blank line, which ends the container and every fence in it.
- **Escaping every line-start HTML tag:** Simpler than Decision 4's fence lookahead, but shows as text every `<div>` or `<details>` line that gnoweb drops today.
- **Exempting `<gno-icon>` at line start:** Rejected because line-start `<gno-icon>` was established and pinned as escaped in existing tests (`block-gno-icon-line-start.txtar`), and allowing it at line-start would diverge from document-level `<gno-…>` line rules.

## Consequences & Upgrade Coordination

- **Security:** `<gno-form>`, `<gno-columns>`, `<gno-frame>`, and future structural extension tags are escaped at block start, including after list and quote markers, after a fence that a list item ends, and on lines the fence tracker counts as code.
- **Integrity:** Unclosed, indented, and list-item fences no longer swallow the realm's chrome or rebind its reference links. `TestExtensionAndFooterIsolation` renders each known shape through `Block`, `BlockRich`, `Blockquote` and `BlockquoteRich` between realm chrome and checks for live `gno-*` elements, a bolded footer, and an unbound `[home]`.
- **Residual:** brackets on a line the fence tracker counts as code but goldmark does not stay unescaped, so a shortcut reference there (`[home]`) can still link to a label the realm defines. It produces link text pointing at the realm's own URL and defines nothing.
- **Fidelity cost:**
  - Rich mode: a fence whose content or closer sits further left than the opener is now closed at that line, whether at document level (indented 1–3 spaces) or inside a list item. ` ```\nfoo\n``` ` and `- a\n   ```\n  x\n   ``` ` render with `foo` / `x` split between two empty code blocks where goldmark alone would render one. Fences whose content is indented at or beyond the opener render as before.
  - Both modes: a block-start `<gno-…>` tag or a `[label]: url` line inside real code shows a backslash, as `<gno-button` already did. A line-start HTML tag followed by a fence line before the next blank line shows as text.
- **Gas:** the two slopes rise by 145% (strict, ×2.45) and 195% (Rich, ×2.95) to cover the slowest title-scan interruption shapes. Blank-line-heavy input already cost about 1.3x per byte more than the calibration shape on the old native, which the new factors also cover.
- **Not addressed here:** an LRD title scan that runs to a line holding a long thematic break (`---…`) checks that line without charging the scan budget, once per candidate whose title reaches it, so `[a]: u\n(x\n` repeated about √n times before such a line costs O(n^1.5). It predates this change (same time before and after) and needs its own fix.
- **Chain Upgrade Requirement:** `gnovm/stdlibs/chain/markdown` is an on-chain native stdlib executed deterministically by GnoVM. Changes to `EscapeBlockHazards` and `EscapeBlockHazardsRich` modify contract execution output, and their gas rows change. This change requires a coordinated protocol upgrade on `gno.land` (and Onyx/testnet) and cannot be deployed unilaterally to production nodes without a coordinated hard fork / scheduled upgrade height.
